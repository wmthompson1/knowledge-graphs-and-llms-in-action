# Source Mapping and Grain Specification

## 1. Modeling principle

The billing query family crosses facts at different grains. The ontology
therefore treats grain as first-class metadata and distinguishes:

- **Trigger facts**: shipment and invoice facts that determine when billing is
  eligible.
- **Evidence facts**: work-order labor, resource, and service-cost facts.
- **Policy facts**: rates, fixed standards, minimums, inclusions, exclusions,
  and exceptions.
- **Result facts**: billing lines generated by applying policy to evidence for a
  trigger.

## 3. Output-grain specification

### ASSY

The final grouping keys are:

`PART_ID, CUSTOMER_ORDER.ID, TOTAL_SHIPPED_QTY, PACKLIST_ID, INVOICED_DATE, INVOICE_ID, ACT_SERVICE_COST`

The intended business grain is:

> One ASSY billing line per part, customer order, shipment/packlist, invoice,
> invoice date, billed quantity basis, and service-cost value.

The result is not naturally a labor-entry fact. Labor entries are many-to-one
inputs aggregated into the billing line.

### 5AXIS

The final grouping adds the part-specific fixed-hour values:

`PART_ID, CUSTOMER_ORDER.ID, TOTAL_SHIPPED_QTY, PACKLIST_ID, INVOICED_DATE,
INVOICE_ID, Setup Time, SFC Count, Run Time`

The intended business grain is:

> One fixed-hour billing line per part, customer order, shipment/packlist,
> invoice, billed quantity basis, and effective fixed-hour standard.

### FINISH

The grouping also includes finish category, fixed-hour values, and batch
quantity. The grain is:

> One finish billing line per billing category, part, customer order,
> shipment/invoice event, quantity basis, and applicable fixed-hour category or
> actual-labor policy.

### EME and MFG

These procedures may combine actual labor, service charges, fixed or minimum
charges, and expedite rules. Their output grain must include the policy identity
in addition to commercial and shipment keys, even when the SQL output currently
exposes the policy only through comments or category fields.

## 4. Grain reconciliation requirement

The query family joins shipment-line triggers to work-order labor through
`DEMAND_SUPPLY_LINK`. A work order can be linked to more than one shipment.
Without an explicit allocation, every shipment can inherit all labor entries
from the work order.

The ontology represents this with:

- `cub:evidenceFromLaborEntry`: direct use of a labor entry by a billing line.
- `cub:supportedByWorkOrder`: the manufacturing job supporting a line.
- `cub:triggeredByShipmentLine`: the shipment fact triggering a line.
- `cub:usesAllocationMethod`: the method reconciling work-order evidence to the
  shipment billing line.
- `cub:allocationFactor`: the fraction of evidence allocated to that line.

A billing line combining work-order labor and shipment triggers without an
allocation method is a control exception unless the work order has exactly one
shipment line in the population.

## 5. Billing methods

| SQL behavior | Ontology method |
|---|---|
| Sum actual setup/run labor | `cub:ActualLaborHoursMethod` |
| Part-specific setup plus run-hours-per-unit times quantity | `cub:FixedStandardHoursMethod` |
| Raise calculated amount to a floor | `cub:MinimumChargeMethod` |
| `SERVICE_CHARGE_ID = 'EX'` handling | `cub:ExpediteChargeMethod` |
| Convert `ACT_SERVICE_COST / SERVICE` to hours | `cub:ServiceCostConversionMethod` |
| Combination of methods | `cub:HybridBillingMethod` |

## 6. Rule precedence

Recommended precedence is explicit and versioned:

1. Determine customer/program/date scope.
2. Apply inclusion rules.
3. Apply general exclusion rules.
4. Apply authorized exception rules that identify the overridden exclusion.
5. Select the calculation method and effective rate schedule.
6. Reconcile evidence grain to billing-line grain.
7. Calculate pre-adjustment amount.
8. Apply minimum, special, service, or expedite adjustments.
9. Emit a billing line with complete provenance.

## 7. Local-code governance

The following fields must remain source codes until formally defined:

- `CUSTOMER_ORDER.ID` displayed as `RAMAC`.
- `SHOP_RESOURCE_SITE.USER_1` used as a resource/billing category.
- `SHOP_RESOURCE_SITE.USER_9` used as include/exclude control.
- `SHOP_RESOURCE_SITE.USER_10` used as a charge or hours override.
- `CUST_ORDER_LINE.SERVICE_CHARGE_ID`, including `EX`.

Use `cub:SourceCodeAssignment` to preserve the raw code and source field. A
separate governed mapping can later connect a code assignment to a
`cub:BillingCategory`, `cub:ResourceClass`, or `cub:ChargeType`.

## 8. Recommended identifiers

- Billing run: program + start date + end date + execution timestamp.
- Billing line: billing run + category + customer order line + packlist +
  invoice + part + policy.
- Rate schedule: report/program + effective-from timestamp.
- Rule: stable rule ID + version/effective-from timestamp.
- Work order: full composite key, never `BASE_ID` alone.
- Customer-order line: customer-order ID + line number.
- Shipment line: packlist + customer-order ID + customer-order line number.
